# 📘 `commons-cache` 模块深度架构白皮书

结合 `JDK 25 + Spring Boot 4 + Spring Cloud Gateway (WebFlux) + Nacos` 的技术栈，`commons-cache` 绝非简单的“Redis
工具类封装”，而是微服务架构中的**高性能数据访问基础设施**。以下从架构定位、功能矩阵、设计原则、实战红线到生态协同，进行系统性拆解。

---

## 一、 为什么设计 `commons-cache`？（背景与痛点）

在微服务演进过程中，缓存使用通常经历三个阶段，痛点逐渐暴露：

| 阶段           | 典型做法                                                          | 暴露的痛点                                     |
|:-------------|:--------------------------------------------------------------|:------------------------------------------|
| **1. 散兵游勇期** | 各服务自行引入 `spring-boot-starter-data-redis`，直接操作 `RedisTemplate` | 代码重复率高；序列化不一致；异常处理混乱；无统一监控                |
| **2. 简单封装期** | 抽取 `RedisUtils` 静态方法，统一 Key 前缀                                | 仍为同步阻塞 API；与 WebFlux 响应式模型冲突；本地缓存与分布式缓存割裂 |
| **3. 架构治理期** | 引入多级缓存、集群同步、动态配置、降级策略                                         | **缺乏统一抽象层**，导致网关与业务服务缓存行为不一致，运维与排查成本激增    |

**`commons-cache` 的诞生使命**：终结“各写各的缓存逻辑”，提供一套**企业级、响应式友好、可观测、高可用**
的多级缓存基础设施，让业务开发聚焦核心逻辑，让运维具备全局掌控力。

## 二、 模块定位与核心作用（架构视角）

| 维度       | 定位说明                                                                                                                                                                                                     |
|:---------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **架构层级** | 位于 `commons` 公共层，属于**横向基础设施模块**，被 `api-gateway` 及所有业务服务依赖                                                                                                                                                |
| **技术定位** | 屏蔽底层缓存实现差异（Caffeine / Redisson / JetCache 等），提供统一抽象接口与运行时引擎                                                                                                                                              |
| **核心作用** | 1️⃣ **性能加速**：L1 本地缓存拦截 90%+ 读请求，降低下游与 Redis 压力<br>2️⃣ **一致性保障**：L1+L2 自动同步，集群数据最终一致<br>3️⃣ **响应式适配**：全面拥抱 `Reactor`，杜绝阻塞线程<br>4️ **容灾降级**：Redis 宕机不雪崩，业务无损运行<br>5️⃣ **可观测内置**：命中率、延迟、驱逐数自动暴露至 Micrometer |

> 📌 **一句话总结**：`commons-cache` 是微服务架构的**“内存加速层 + 分布式协调器 + 流量缓冲垫”**。

## 三、 核心功能矩阵与预期效果

| 功能域            | 具体能力                                                                                | 预期效果                              |
|:---------------|:------------------------------------------------------------------------------------|:----------------------------------|
| 🧩 **多级缓存引擎**  | L1 (Caffeine) + L2 (Redis) 自动协同；支持 `get/put/invalidate` 语义                          | L1 命中率 >95%，P99 延迟 <2ms；内存可控不 OOM |
| ⚡ **响应式适配**    | 提供 `Mono<V> getAsync()` / `Flux<V> listAsync()`；内置 `Schedulers.boundedElastic()` 隔离 | WebFlux 网关不阻塞事件循环，QPS 提升 3~5 倍    |
| **集群同步机制**     | Redis Pub/Sub 广播失效；支持事件驱动清理 L1；断线重连自动补偿                                             | 集群数据不一致窗口 <50ms；重启自动清空脏 L1        |
| ⚙️ **动态配置热刷新** | TTL、容量、淘汰策略绑定 Nacos；支持 `@RefreshScope` 实时生效                                         | 扩容/调参无需重启；压测期间可动态降载               |
| 🛡️ **降级与容灾**  | Fail-Open（放行）/ Fail-Closed（拒绝）策略可配置；本地兜底模式                                          | Redis 宕机时业务无损；核心链路不中断             |
| 📊 **可观测性集成**  | 自动注册 `CacheMetrics`；暴露 `cache.hits/misses/evictions/latency`                        | 接入 Prometheus/Grafana；异常命中率秒级告警   |
| 🔒 **安全与规范**   | Key 自动加业务前缀；Value 统一 JSON 序列化；敏感字段自动脱敏                                              | 避免 Key 冲突；日志不泄露业务数据；序列化兼容多语言      |

## 四、 架构设计原则（指导思想）

设计 `commons-cache` 必须坚守以下 6 条架构原则：

| 原则                                      | 内涵                        | 落地体现                                                |
|:----------------------------------------|:--------------------------|:----------------------------------------------------|
| **1. 抽象隔离 (Abstraction First)**         | 业务代码只依赖接口，不感知底层实现         | 提供 `MultiLevelCache<K,V>` 接口；通过 SPI/AutoConfig 切换实现 |
| **2. 响应式优先 (Reactive-First)**           | 全面适配 Project Reactor，严禁阻塞 | 所有 L2 查询返回 `Mono/Flux`；同步 API 仅保留给传统 Servlet 场景     |
| **3. 配置驱动 (Config-Driven)**             | 策略外部化，支持热更新               | TTL、容量、降级模式全走 `application.yaml` + Nacos            |
| **4. 防御性设计 (Defensive)**                | 内置防穿透/雪崩/击穿；故障自动降级        | 空值缓存短 TTL；L1 设 `maximumSize`；异常走 `onErrorResume`    |
| **5. 可观测内置 (Observability by Default)** | 指标、日志、链路追踪开箱即用            | 集成 Micrometer；操作日志带 TraceId；暴露 `/actuator/metrics`  |
| **6. 轻量无侵入 (Lightweight)**              | 最小依赖，不污染业务上下文             | 仅依赖 `caffeine`、`redisson`、`reactor-core`；不引入重量级框架   |

## 五、 关键注意事项与避坑指南（实战红线）

| 风险维度                | 典型陷阱                                         | 正确做法                                                                     | 后果对比                           |
|:--------------------|:---------------------------------------------|:-------------------------------------------------------------------------|:-------------------------------|
| **🔁 一致性边界**        | L1 与 L2 TTL 相同；先清 L1 再写 L2                   | `L1_TTL ≪ L2_TTL`；更新顺序：`先写 L2/DB → 后失效 L1`                               | ❌ 脏读 / ✅ 最终一致+自愈               |
| **⚡ 线程模型**          | 在 Gateway Filter 中同步调用 `redisTemplate.get()` | 使用 `Mono.fromCallable().subscribeOn(boundedElastic())` 或 Redisson 异步 API | ❌ 阻塞 Reactor 线程，网关假死 / ✅ 异步非阻塞 |
| **📦 内存控制**         | Caffeine 不设 `maximumSize`；缓存大对象/完整 Entity    | 必设容量上限；Value 存精简 DTO/ID/标记；开启 `recordStats()`                            | ❌ OOM / ✅ 内存平稳，可监控             |
| **🔑 Key/Value 规范** | 直接存完整 JWT 字符串；使用 Java 原生序列化                  | Key 用 `jti` 或短哈希；Value 统一 JSON/String；禁用 `Serializable`                  | ❌ 内存碎片+跨语言失败 / ✅ 紧凑+兼容         |
| **🛡️ 降级策略**        | Redis 宕机直接抛异常，导致 500 雪崩                      | 核心鉴权用 `Fail-Open`（放行+告警），配置类用 `Fail-Closed`（拒绝或查 DB）                     | 级联故障 / ✅ 业务无损                  |
| **📡 Pub/Sub 可靠性**  | 依赖消息必达，节点重启不处理 L1                            | 消息可能丢失，依赖 L1 TTL 自愈；重启时主动 `cache.invalidateAll()`                        | ❌ 残留黑名单 Token / ✅ 脏数据自动清理      |

## 六、 与微服务生态的协同关系

`commons-cache` 不是孤岛，而是架构拼图的**核心连接件**：

| 协同模块                                | 交互方式                                                   | 价值                      |
|:------------------------------------|:-------------------------------------------------------|:------------------------|
| `commons-core`                      | 共享基础异常类、线程池工具、Result 封装                                | 统一错误语义，降低耦合             |
| `commons-security`                  | 注入 `tokenBlacklistCache` 实例                            | 网关鉴权性能提升 10 倍，踢人实时生效    |
| `api-gateway`                       | 集成限流计数器、路由配置缓存、IP 封禁表                                  | 网关吞吐量突破 2w+ QPS，配置秒级热更新 |
| `commons-web` / 业务服务                | 提供 `@Cacheable` 增强注解、缓存拦截器                             | 业务代码零缓存样板，聚焦领域逻辑        |
| `commons-logging` / `commons-trace` | 缓存操作日志自动脱敏；TraceId 透传；Micrometer 指标聚合                  | 全链路可观测；缓存命中率异常秒级定位      |
| `mall-cloud-dependencies`           | 统一版本管理（Caffeine 3.x, Redisson 3.35+, Micrometer 1.13+） | 避免依赖冲突；升级只需改父 POM       |

## 七、 典型场景映射与决策矩阵

| 场景类型           | 是否适合 `commons-cache` | 推荐策略                                     | 备注                        |
|:---------------|:---------------------|:-----------------------------------------|:--------------------------|
| ✅ JWT 黑名单/风控规则 | **强烈推荐**             | L1 60s + L2 30d + Pub/Sub 失效 + Fail-Open | 网关核心场景，性能收益最大             |
| ✅ 热点商品/字典配置    | **强烈推荐**             | L1 300s + L2 1h + 随机 TTL 防雪崩             | 读多写少，多级缓存最佳实践             |
| ✅ 限流计数/滑动窗口    | **推荐**               | L1 本地聚合 + 定时/阈值刷 L2                      | 降低 Redis 写入压力，允许轻微延迟      |
| ✅ 用户会话/权限树     | **推荐**               | L1 按访问淘汰 + L2 持久化 + 主动失效                 | 下游免解析 JWT，开发体验提升          |
| 🚫 账户余额/支付状态   | **不推荐**              | 走 DB + Seata 分布式事务                       | 强一致性场景，缓存仅作查询加速（需标明“非实时”） |
| 🚫 高频写入流水/日志   | **不推荐**              | 直接落库或走 MQ 异步处理                           | 写多读少，缓存反而增加一致性成本          |

## 八、 总结：从“工具类”到“基础设施”的演进

`commons-cache` 的设计哲学可以概括为：

> **“用架构的复杂度，换取性能的确定性；用抽象的边界，守住一致性的底线。”**

它不是银弹，而是一套**工程权衡体系**：

- 对开发者：屏蔽底层细节，提供声明式、响应式、可观测的 API
- 对架构师：统一缓存治理，提供降级、限流、热更新、集群同步能力
- 对运维：暴露标准化指标，支持动态调优与故障自愈

只要坚守 **`异步非阻塞、L1L2、先写后失效、故障可降级、指标全暴露`** 五条红线，`commons-cache` 就能成为你 `mall-cloud`
架构中最坚实、最安静的性能引擎。
