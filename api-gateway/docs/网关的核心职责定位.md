作为微服务架构的“统一流量入口”，`api-gateway` 的设计质量直接决定了整个系统的**安全性、稳定性、可观测性与扩展性**。结合你使用的
**JDK 25 + Spring Boot 4 + Spring Cloud Gateway + Nacos** 技术栈，下面从职责、功能、架构设计、代码结构到避坑指南进行系统化梳理。

## 🎯 一、网关的核心职责定位（4大维度）

| 维度       | 职责说明                  | 边界原则               |
|----------|-----------------------|--------------------|
| **流量路由** | 请求分发、协议转换、路径重写、负载均衡   | 只做转发，不处理业务逻辑       |
| **安全管控** | 认证鉴权、限流防刷、黑白名单、数据脱敏   | 安全策略统一收敛，业务服务免重复实现 |
| **流量治理** | 熔断降级、灰度发布、权重路由、超时重试   | 保护下游服务，防止雪崩        |
| **可观测性** | 访问日志、链路追踪、指标采集、异常统一返回 | 提供标准化监控数据，不拦截正常业务流 |

> 📌 **核心原则**：网关是“交通警察”和“安检口”，不是“办事大厅”。复杂业务、数据聚合、状态管理一律下沉到下游微服务。

## 🏗️ 三、网关架构设计原则（5条铁律）

1. **无状态化**：网关不保存会话/业务状态，所有状态由下游服务或 Redis 管理，便于水平扩缩容。
2. **异步非阻塞**：Spring Cloud Gateway 基于 WebFlux/Reactor，**严禁在过滤器中使用同步阻塞 API**（如 `Thread.sleep`、JDBC
   直连）。如需调用外部同步服务，使用 `Schedulers.boundedElastic()` 或虚拟线程包装。
3. **配置与代码分离**：路由规则、限流阈值、白名单列表等尽量放在 Nacos 配置中心，支持 `@RefreshScope` 热更新，减少重启。
4. **过滤器链精简**：全局过滤器数量控制在 5~8 个以内，避免链路过长导致延迟叠加。按 `@Order` 严格排序。
5. **高可用部署**：多实例部署 + 前端负载均衡器（Nginx/ALB/云厂商 LB），网关自身也要纳入健康检查与自动重启策略。

### 🔑 关键配置示例 (`application.yml`)

```yaml
spring:
  application:
    name: api-gateway
  cloud:
    gateway:
      # 关闭自动路由，避免意外暴露
      discovery:
        locator:
          enabled: false
      # 全局默认过滤器
      default-filters:
        - name: Retry
          args:
            retries: 2
            statuses: BAD_GATEWAY,SERVICE_UNAVAILABLE
            methods: GET
      # HTTP 客户端优化
      httpclient:
        connect-timeout: 3000
        response-timeout: 30s
        pool:
          type: elastic
          max-connections: 1000
          max-idle-time: 30s
    nacos:
      discovery:
        server-addr: ${NACOS_ADDR:localhost:8848}
      config:
        server-addr: ${NACOS_ADDR:localhost:8848}
        refresh-enabled: true

# 监控与追踪
management:
  endpoints:
    web:
      exposure:
        include: health,info,gateway,metrics
  metrics:
    tags:
      application: ${spring.application.name}
```

## 五、过滤器链执行顺序设计（核心！）

网关性能与稳定性高度依赖过滤器链的排序。推荐顺序如下：

| 顺序 | `@Order` 值                   | 过滤器                     | 职责                          | 注意事项                                              |
|----|------------------------------|-------------------------|-----------------------------|---------------------------------------------------|
| 1  | `Ordered.HIGHEST_PRECEDENCE` | `CorsPreflightFilter`   | 快速放行 OPTIONS 预检请求           | 避免后续过滤器浪费资源                                       |
| 2  | `-200`                       | `TraceGlobalFilter`     | 生成/透传 `X-Trace-Id`，放入 MDC   | 必须在最前，保证全链路可追踪                                    |
| 3  | `-100`                       | `AuthGlobalFilter`      | JWT 校验、白名单放行、注入 `X-User-ID` | 你已优化，注意 `request.mutate()` 生效                     |
| 4  | `0`                          | `RateLimitGlobalFilter` | 限流检查（IP/用户维度）               | 限流应在认证之后，避免恶意请求消耗配额                               |
| 5  | `100`                        | `LogGlobalFilter`       | 记录请求方法、路径、耗时、状态码            | 使用 `exchange.getResponse().beforeCommit()` 捕获最终状态 |
| 6  | `Integer.MAX_VALUE`          | 路由转发                    | Spring Cloud Gateway 内置路由逻辑 | 自动执行，无需手动编写                                       |

> ⚠️ **过滤器开发铁律**：
> - 所有过滤器必须返回 `Mono<Void>`，禁止阻塞线程
> - 修改请求必须通过 `exchange.mutate().request(newRequest).build()` 回写
> - 异常处理使用 `onErrorResume` 或统一 `ErrorWebExceptionHandler`

## 六、结合 JDK 25 / Spring Boot 4 的现代化优化

| 特性                         | 网关应用方式                                                                                                                     | 收益                             |
|----------------------------|----------------------------------------------------------------------------------------------------------------------------|--------------------------------|
| **虚拟线程 (Virtual Threads)** | 网关本身是 WebFlux 异步模型，**不需要**改为虚拟线程。但若网关内调用外部同步 HTTP 客户端（如旧版 RestTemplate），可包裹进 `Executors.newVirtualThreadPerTaskExecutor()` | 避免阻塞 Reactor 事件循环，提升吞吐量        |
| **GraalVM Native Image**   | 网关编译为原生镜像，启动时间 < 0.5s，内存占用 < 50MB                                                                                          | 适合 Serverless、K8s 快速扩缩容、边缘节点部署 |
| **HTTP/3 (QUIC) 支持**       | Spring Boot 4 + Netty 原生支持 HTTP/3，配置 `server.http3.enabled=true`                                                           | 弱网环境下移动端访问延迟降低 30%+            |
| **Structured Logging**     | 使用 `logstash-logback-encoder` 输出 JSON 日志，自动注入 `traceId`、`userId`                                                           | ELK/Loki 检索效率提升，支持告警规则         |
| **Micrometer Tracing**     | 替换 Sleuth，原生支持 OpenTelemetry，自动上报 SkyWalking/Jaeger                                                                        | 标准化可观测性，多云厂商兼容                 |

## ️ 七、常见陷阱与避坑指南

| 陷阱                                | 后果                  | 解决方案                                              |
|-----------------------------------|---------------------|---------------------------------------------------|
| 在过滤器中调用 `Thread.sleep()` 或同步 JDBC | 阻塞 Reactor 线程池，网关假死 | 使用 `Mono.delay()` 或 `Schedulers.boundedElastic()` |
| JWT 密钥硬编码或未缓存                     | 每次请求都查库/解析，CPU 飙升   | 启动时加载密钥到内存，使用 `Caffeine` 缓存公钥                     |
| 限流规则未做并发安全控制                      | 高并发下限流失效或误杀         | 使用 Redis + Lua 脚本或 Sentinel 原生计数器                 |
| 日志打印完整请求体（含密码/Token）              | 安全合规风险，磁盘打满         | 脱敏处理，仅记录关键头信息，大报文采样记录                             |
| 网关直接返回下游 500 错误堆栈                 | 暴露内部架构，用户体验差        | 统一 `ErrorWebExceptionHandler` 转换为标准 JSON          |
| 路由配置写死在 YAML                      | 扩容/灰度需重启网关          | 路由规则放入 Nacos，监听 `RouteDefinition` 事件动态刷新          |

## ✅ 八、总结：网关设计检查清单

- [ ] 是否只依赖 `commons-core`、`commons-security`、`commons-logging`、`commons-trace`？（避免依赖爆炸）
- [ ] 是否关闭了 `discovery.locator.enabled`？（防止服务意外暴露）
- [ ] JWT 过滤器是否正确使用 `exchange.mutate()` 回写请求？
- [ ] 限流、熔断规则是否支持 Nacos 热更新？
- [ ] 是否统一处理了 OPTIONS 预检请求？
- [ ] 日志是否脱敏且结构化输出？
- [ ] 是否暴露了 `/actuator/gateway/routes` 用于运维排查？
- [ ] 压测 QPS 是否达到预期？（通常单机 2k~5k QPS 属正常）
