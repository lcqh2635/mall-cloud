这是一个非常经典且核心的架构问题。

**简短的回答是：非常有必要，而且是“必须”的。**
但需要注意的是，**网关的鉴权和业务服务的鉴权，职责是完全不同的。**

在微服务架构中，网关不仅仅是一个路由器，它更是整个系统的**“安检口”**。如果不做统一鉴权，你的微服务系统将面临巨大的安全风险和性能浪费。

以下是详细的分析，解释为什么网关必须做 Auth，以及它和业务服务该如何分工：

### 1. 为什么网关必须做鉴权？（三大核心理由）

#### ① **拦截非法流量，保护下游服务（性能层面）**

* **场景**：如果有恶意用户或者爬虫，不带 Token 或者带个假 Token 疯狂请求你的接口。
* **不做网关鉴权**：请求会穿透网关，到达 `user-service` 或 `order-service`。下游服务拿到 Token 后，发现是假的，拒绝请求。
    * *后果*：下游服务白白消耗了 CPU（解析 Token）、内存和网络连接来处理这些垃圾请求。
* **做网关鉴权**：网关在入口处发现 Token 无效，直接返回 401。
    * *优势*：**请求根本不会到达下游服务**。这极大地保护了脆弱的业务服务，防止被恶意流量打挂。

#### ② **统一安全标准，避免“漏网之鱼”（安全层面）**

* **场景**：你有 10 个微服务。
* **不做网关鉴权**：你需要在 10 个服务里分别写 JWT 校验逻辑，配置 Security 过滤器。
    * *风险*：只要有一个新来的程序员开发 `promotion-service`（促销服务）时忘了配拦截器，或者配错了白名单，这个服务就“裸奔”了。黑客可以直接绕过网关调用这个服务。
* **做网关鉴权**：所有外部流量必须经过网关。只要网关这扇门守住了，下游服务即使“裸奔”（仅限内网暴露），外部也访问不到。

#### ③ **上下文透传，简化下游开发（架构层面）**

* **场景**：下游服务需要知道“当前是谁在请求”。
* **不做网关鉴权**：每个下游服务都要重复写：解析 Token -> 校验签名 -> 提取 UserID -> 放入 SecurityContext。代码重复率 100%。
* **做网关鉴权**：网关统一解析 Token，提取出 `UserID`、`Roles`，放入 HTTP Header（如 `X-User-Id`）转发给下游。
    * *优势*：下游服务只需要读 Header 就能拿到用户信息，**不需要再解析 Token**，开发效率大幅提升。

---

### 2. 网关 vs 下游服务：鉴权职责如何划分？

这是最关键的设计点。很多人误以为网关做了鉴权，下游就不用管了，这是错误的。

| 维度       | **API Gateway (网关)**                                                                     | **Microservices (业务服务)**                                                                       |
|:---------|:-----------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------|
| **核心职责** | **认证 (Authentication)**                                                                  | **授权 (Authorization)**                                                                         |
| **通俗解释** | **“你是谁？”** (验明正身)                                                                        | **“你能干什么？”** (权限控制)                                                                            |
| **具体动作** | 1. 检查 Token 是否存在<br>2. 校验 Token 签名是否合法<br>3. 检查 Token 是否过期<br>4. **提取 UserID 放入 Header** | 1. 从 Header 读取 UserID<br>2. 检查该 UserID 是否有权限访问此接口 (如 `@PreAuthorize`)<br>3. 检查数据权限 (如只能看自己的订单) |
| **技术实现** | `GlobalFilter` (JWT 校验)                                                                  | Spring Security `MethodSecurity` / AOP                                                         |
| **处理结果** | 无效 -> 直接打回 (401)<br>有效 -> 放行并注入信息                                                        | 无权 -> 拒绝访问 (403)<br>有权 -> 执行逻辑                                                                 |

**最佳实践流程：**

1. **请求到达网关** -> 网关校验 JWT 签名和过期时间 -> **通过**。
2. **网关透传** -> 将 `User-Id: 1001` 写入 Request Header -> 转发给 `order-service`。
3. **Order-Service 接收** -> 拦截器读取 Header 中的 `User-Id` -> 设置到当前线程上下文。
4. **Controller 执行** -> 发现接口标注了 `@PreAuthorize("hasRole('ADMIN')")` -> 检查用户角色 -> **通过/拒绝**。

### 3. 需要注意的“坑” (针对你的项目)

既然决定在网关做统一鉴权，有几个技术细节必须注意，否则会成为性能瓶颈：

#### A. 性能问题：JWT 校验必须是“本地计算”

* **正确做法**：JWT 的校验（签名验证）应该是纯 CPU 计算，**不需要查数据库或 Redis**。网关拿到 Token，用本地缓存的 Secret Key
  一算就知道真假。这样速度极快（微秒级）。
* **错误做法**：网关拿到 Token 后，去 Redis 查一下这个 Token 是否存在，或者去数据库查用户状态。
    * *后果*：每个请求都要经过一次网络 I/O，网关会瞬间成为瓶颈，QPS 直线下降。
    * *解决方案*：如果必须校验 Token 是否被拉黑（黑名单），建议使用高性能的 Redis 客户端，或者采用“短有效期 Access Token +
      刷新机制”，容忍极小概率的已注销用户还能访问几分钟。

#### B. 内部服务调用 (Feign) 怎么办？

* 微服务之间会通过 Feign 互相调用（例如 Order 调 User）。这些调用是**不经过网关**的。
* **问题**：如果下游服务只信任网关传来的 Header，那内部调用怎么办？
* **解决方案**：
    1. **传递 Token**：Feign 拦截器将网关透传下来的 Token 继续传给下一个服务（适合全链路追踪）。
    2. **Service-to-Service Token**：内部服务使用一种特殊的、生命周期很长的内部 Token，或者配置 IP 白名单，允许内部直接调用。

### 4. 总结

**网关必须做统一鉴权（Authentication），这是微服务架构的“底线”。**

* 它负责**挡掉无效请求**，保护后端。
* 它负责**统一解析用户身份**，减轻后端负担。
* 它负责**建立安全屏障**，防止配置遗漏导致的裸奔。

你的 `JwtTokenFilter` 设计是非常正确的方向。只要确保校验逻辑是**非阻塞**的（对于 WebFlux 网关至关重要）且**不依赖外部 I/O**
，这就是最完美的架构设计。
