## ✅ 一、保险系统核心业务逻辑全景图（生命周期驱动）

保险业务的核心是围绕“**保单的生命周期**”展开的，从客户产生购买意向，到保单终止，整个过程包含多个关键阶段：

> 🎯 保单生命周期 = 投保 → 核保 → 承保 → 缴费 → 保全 → 理赔 → 续保/满期/退保 → 注销/终止

---

## 🧩 二、各阶段详细业务逻辑说明（适合后端开发理解）

---

### 1️⃣ 投保（Application）

> 客户填写投保信息，发起投保申请

**业务逻辑要点：**

- 客户身份验证（姓名、身份证、银行卡、手机号）
- 产品选择（险种、保额、缴费年限、保障期限）
- 保费试算（根据年龄、性别、职业、保额等因子计算）
- 风险测评（监管要求，匹配客户风险等级与产品风险等级）
- 健康告知（寿险/重疾险需填写健康问卷）
- “双录”（银行渠道销售需录音录像，绑定保单号）
- 生成投保单（Application Form），状态为“待核保”

**后端开发关注点：**
- 表单校验、风控规则引擎调用
- 试算服务（可缓存产品费率表）
- 双录文件上传与关联（文件服务 + 元数据存储）
- 生成唯一投保单号（分布式ID，如雪花算法）

---

### 2️⃣ 核保（Underwriting）

> 保险公司评估风险，决定是否承保、加费、除外或拒保

**业务逻辑要点：**

- 自动核保（规则引擎判断：年龄、保额、健康告知答案等）
- 人工核保（触发条件：高保额、有病史、职业风险高等）
- 核保结论：标准体、加费、责任除外、延期、拒保
- 核保通知（短信/APP推送客户）

**后端开发关注点：**
- 对接保险公司核保接口（同步 or 异步）
- 状态机管理（投保单状态流转）
- 核保规则配置化（可使用 Drools 或自研规则引擎）
- 异常处理（超时、失败重试、人工介入流程）

---

### 3️⃣ 承保（Policy Issuance）

> 核保通过后，正式生成保单，合同生效

**业务逻辑要点：**

- 生成正式保单号（Policy Number）
- 计算首期保费、缴费日期
- 保单条款、现金价值表、电子合同生成
- 支付状态联动（未支付则不生效）
- 生效日设定（T+0 或 T+1 或指定日期）
- 通知客户保单生效

**后端开发关注点：**
- 支付与承保状态一致性（分布式事务 or 最终一致性）
- PDF 电子保单生成（iText / JasperReport / 模板引擎）
- 保单数据落库（客户、险种、受益人、保费等）
- 推送通知（短信、微信、站内信）

---

### 4️⃣ 缴费（Premium Payment）

> 客户缴纳保费（首期 + 续期）

**业务逻辑要点：**

- 首期缴费（投保时支付）
- 续期缴费（按年/月自动扣款或提醒）
- 宽限期（通常60天，宽限期内保障仍有效）
- 失效（宽限期后未缴费 → 保单效力中止）
- 复效（补缴保费+利息，重新核保，恢复效力）

**后端开发关注点：**
- 定时任务扫描待缴费保单（Quartz / XXL-JOB）
- 对接银行代扣接口（银企直连 or 支付平台）
- 缴费状态同步（支付成功 → 更新保单状态）
- 生成缴费记录、发票（电子发票对接）

---

### 5️⃣ 保全（Policy Servicing）

> 保单生效后，客户申请变更信息或权益

**常见保全项目：**

- 变更受益人、地址、手机号
- 部分领取（年金险）、减保
- 退保（犹豫期内全额退，犹豫期外按现金价值退）
- 保单贷款（寿险特有）
- 复效申请（补缴保费恢复效力）

**后端开发关注点：**
- 权限控制（谁可以申请保全？投保人？被保人？）
- 审批流（大额退保需人工审核）
- 数据一致性（变更后历史留痕）
- 与核心系统同步（银行侧申请 → 保险公司执行）

---

### 6️⃣ 理赔（Claim）

> 发生保险事故后，客户申请赔付

**业务逻辑要点：**

- 报案登记（时间、事故描述、材料清单）
- 材料上传（病历、发票、死亡证明等）
- 理赔审核（自动 or 人工）
- 理赔结论（给付、拒赔、协议赔付）
- 赔款支付（打款到客户账户）
- 结案归档

**后端开发关注点：**
- 材料OCR识别（可选，AI集成）
- 状态机流转（报案 → 受理 → 审核 → 结案）
- 与支付系统对接
- 理赔规则引擎（是否符合理赔条件）

> ⚠️ 注意：在银行渠道，理赔通常由保险公司处理，银行系统只做报案入口或状态展示。

---

### 7️⃣ 续保 / 满期 / 退保（Policy Termination）

- **续保**：一年期产品（如医疗险）到期前自动/手动续保
- **满期**：长期险到期，返还满期金（如两全保险）
- **退保**：客户主动终止合同，返还现金价值
- **注销**：保单终止，状态归档

**后端开发关注点：**
- 到期提醒（短信、APP推送）
- 满期金计算与支付
- 退保金额计算（现金价值表）
- 数据归档策略（监管要求保留至少5~10年）

## 🔄 三、贯穿始终的核心支撑逻辑

除了生命周期主线，还有以下通用业务逻辑：

### 1. 客户管理（360°视图）
- 客户基本信息、风险等级、KYC、购买历史、持有保单、受益人关系
- 一个客户可持有多张保单

### 2. 产品管理
- 产品定义（险种、条款、费率表、保障责任、现金价值表）
- 产品上下架、区域销售限制、渠道限制

### 3. 佣金与分润
- 银行理财经理销售提成计算
- 银行与保险公司分润对账
- 佣金发放（T+1月 or 季度结算）

### 4. 合规与审计
- 所有操作留痕（谁、何时、做了什么）
- 数据不可删除（只能标记“已注销”）
- 满足监管报送（如银保监EAST、保险业监管数据平台）

### 5. 通知与提醒
- 状态变更通知（承保成功、缴费提醒、理赔进度）
- 多通道：短信、微信、APP、邮件

## 🧱 四、推荐后端建模方式（简化版ER示意）

```java
// 示例：保单聚合根（领域驱动设计思想）
class Policy {
    String policyNo;           // 保单号
    String applicationNo;      // 投保单号
    Customer insured;          // 被保人
    Customer policyHolder;     // 投保人
    List<Beneficiary> beneficiaries; // 受益人列表
    Product product;           // 产品
    BigDecimal premium;        // 保费
    LocalDate effectiveDate;   // 生效日
    PolicyStatus status;       // 状态（新单/生效/失效/退保/终止）
    List<PremiumRecord> premiums; // 缴费记录
    List<EndowmentRecord> endowments; // 保全记录
    List<Claim> claims;        // 理赔记录
}
```

## 🧭 五、给Java后端开发的建议

| 关注点 | 建议 |
|--------|------|
| 状态机 | 使用状态模式或状态机框架（如 Squirrel、Spring State Machine）管理保单状态流转 |
| 规则引擎 | 复杂核保/理赔规则建议用规则引擎（Drools / 自研表达式引擎） |
| 事务一致性 | 投保+支付+承保建议用“本地消息表”或“Seata TCC”保证最终一致 |
| 日志审计 | 所有写操作记录操作日志（OperatorLog），满足合规 |
| 接口适配 | 对接多家保险公司？封装 Adapter 层屏蔽差异 |
| 性能优化 | 产品试算、现金价值查询等高频读，用 Redis 缓存费率表 |

## ✅ 总结一句话：

> **保险系统的业务逻辑 = 以保单生命周期为主线 + 客户/产品/规则/合规为支撑 + 状态机+规则引擎+分布式事务为技术实现手段**

你作为后端开发，不仅要实现功能，更要理解每一个字段、每一个状态变更背后的**业务含义和合规要求**。这样你写的代码才不会“跑偏”，也更容易和BA、测试、业务方高效沟通。
